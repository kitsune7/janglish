Janglish: How It Works

A guided tour of a system that teaches machines to follow a conversation as it hops between Japanese and English — mid-sentence.

1The Big Picture

People who live between two languages rarely speak just one of them. A bilingual Japanese-English speaker will happily say:

娘はとてもindependentで、いつも自分でchoiceをしたがります。

Linguists call this code-switching; this project calls it Janglish. And it breaks speech recognition. Whisper — the workhorse open transcription model — decodes each pass under a single language assumption. Run it in Japanese mode over the sentence above and the word independent comes back as katakana soup (「インディペンデント」-ish, if you're lucky). Run it in English mode and the Japanese comes back as mangled romaji or hallucinated English. Whisper isn't wrong about the sounds; it's wrong about which language's spelling system to write them in — and it has no way to change its mind halfway through a clip.

The insight behind this repository is that you don't need to retrain Whisper. You need a small, fast referee that watches the audio and says, every 20 milliseconds, "this instant is Japanese" or "this instant is English." With that timeline in hand, you can run Whisper in the right language over the right stretches and stitch the results together.

Key concept — frame-level LID

Language identification (LID) usually means labeling a whole clip ("this recording is French"). This project does something finer: frame classification. The model emits one EN/JA decision per frame — a 20 ms slice of audio (320 samples at 16 kHz, i.e. 50 frames per second). A five-second clip becomes a string of ~250 tiny language decisions, which trace exactly where the speaker switched.

That referee is a fine-tuned wav2vec2-xls-r-300m with a frame-classification head, and the best checkpoint in models/lid-wav2vec2-f1-98 reaches 97.7% frame accuracy and 0.976 macro F1 on held-out speakers. But the model is arguably the least interesting part. The interesting part is where its training data comes from — because nobody has a corpus of Japanese-English code-switched speech with per-20ms language labels, and no human wants to produce one by hand.

2Manufacturing Sentences

Before you can synthesize code-switched speech, you need code-switched text — thousands of sentences that hop between languages the way real bilinguals do. Writing them by hand doesn't scale, so cmd/gen_mixed/generate.py asks Claude (via AWS Bedrock) to write them. But an LLM given a vague prompt produces mush, so the script is really a small manufacturing operation: precise specifications going in, ruthless quality control coming out.

The order book: direction × switch count

Every sentence is ordered against a two-dimensional spec. The direction says which language provides the grammatical skeleton: JP_BASE sentences are structurally Japanese with English words dropped in; EN_BASE is the reverse. The cs_level counts islands — distinct runs of the minority language separated by the base language.

Key concept — islands

An island is one contiguous run of minority-language text. In 「今日はmeetingとlunchがありました」 there are two English islands. Two adjacent English words with nothing between them — 「新しいlaptop tabletを…」 — count as one island, because acoustically there is only one switch into English and one switch back. Islands are what the LID model must detect, so the dataset is bucketed by island count.

The targets are explicit in the code, and they deliberately taper — many simple sentences, fewer gymnastic ones:

BucketEN_BASE targetJP_BASE target
cs-2 (two islands)3,3883,496
cs-3 (three islands)1,8501,850
cs-4 (four or more)500500

Each generation request also carries a random theme (from a list of forty: "office work and meetings", "pets and animals", "banking and money"…) and a random batch-id salt, both there to stop the model from converging on the same twenty sentences over and over. A real output row from data/cs-multi.csv:

cs_level|direction|sentence
2|EN_BASE|The 一番 cocktail here has such a good 後味.
2|EN_BASE|Can you recommend a 飲み放題 option that isn't too 高め?

The validation gauntlet in cmd/gen_mixed/generate.py. Each gate exists because of a specific way bad text would poison the audio or the labels.

Gate 2 deserves a pause, because it's the most instructive. Why ban sushi? Because "sushi" is pronounced essentially identically in English and Japanese. If it appears as an "English island" in a Japanese sentence, the audio at that spot carries no acoustic evidence of a language switch — yet the label says one happened. That's not training data; that's label noise wearing a costume. The same logic bans anime, Tokyo, Nintendo, and about ninety other shared-phonology words and proper nouns.

Gate 3 fixes a subtler bug that once stalled the JP_BASE cs-4 bucket entirely. "Primarily Japanese" was originally judged by character count — but a Japanese sentence stuffed with four English islands can have more Latin characters than Japanese ones while still being grammatically Japanese. The fix: judge by grammar, not census. Hiragana (particles like は・が・を, verb endings) signals a Japanese skeleton; English function words (the, is, of, my…) signal an English one. A sentence like 「彼はmeetingでpresentationをしてからclientにemailとreportを送りました」 is majority-Latin by character count but passes as JP_BASE, correctly.

Island counting itself (Gate 5) is charmingly mechanical: classify every character as Japanese script, Latin letter, or ignorable; run-length encode; count runs of the minority language. Which language counts as "minority" isn't inferred — it's known from the generation direction, which is more robust on borderline sentences.

# count_islands("今日はmeetingとlunchとpresentationがありました。", "e")
# char classes:  jjj eeeeeee j eeeee j eeeeeeeeeeee jjjjjjj
# runs:          [j, e, j, e, j, e, j]
# runs.count("e") = 3   →  this is a cs-3 sentence
Engineering note — resumability

The generator is designed to be killed and restarted. On startup it re-reads cs-multi.csv, rebuilds per-bucket counts and the dedup set, and only orders what's still missing. Because validation rejects ~20% of lines, the work queue is over-provisioned by 20%, and if buckets are still short when the queue drains, "top-up rounds" enqueue more batches — up to 40 of them. The whole thing runs 8 threads against Bedrock and prints a running ETA.

Splicing into the manifest

Validated sentences aren't training data until they have a place in data/data-pairs.csv. The companion script splice_cs.py assigns each new sentence a path like synthetic/cs-2/cs7395.flac — continuing each block's numbering — and inserts the rows at the end of the matching cs-N block, keeping the file's order (cs-2, then cs-3, then cs-4; EN-primary before JP-primary within each). It's idempotent: sentences already present are skipped, so you can re-run it after every generation session. At this point the manifest has rows pointing at audio files that don't exist yet. Creating them is the next section's job.

3From Text to Labeled Audio

Now the clever part. We have 14,000 sentences and a manifest full of paths to audio that doesn't exist. cmd/audio_gen/generate_audio.py (the largest file in the repo, and it earns every line) turns each sentence into a spoken clip and — this is the whole point — a label for every 20 ms of it, with no human in the loop.

Step 1: split the sentence into spans

Unicode does the first job for free. Every character is classified by script — hiragana/katakana/kanji ranges are Japanese, ASCII letters are English, and everything else (punctuation, digits, spaces) is "neutral" and attaches to the preceding span, so a trailing 。 or comma stays with the span that produced it (TTS prosody depends on this). Our running example splits into five spans:

娘はとてもindependentで、いつも自分でchoiceをしたがります。

Step 2: render the whole sentence twice

The synthesizer is XTTS v2 with voice cloning: give it a few seconds of a reference speaker (from data/speaker-clips/en and jp, ~100 speakers each) and it speaks any text in that voice. But XTTS, too, wants one language per call. So the script renders the entire sentence twice with the same cloned voice:

EN render  language="en"
"musume wa totemo independent de, itsumo jibun de choice wo shitagarimasu" — Japanese spans converted to romaji
JA render  language="ja"
「娘はとてもindependentで、いつも自分でchoiceをしたがります。」 — original mixed script
↓forced alignment finds each span in each render
Stitched output
JA spans cut from the JA render + EN spans cut from the EN render, joined with 25 ms crossfades
Two full-sentence renders, one output. The same speaker latents drive both renders, so the stitched voice is consistent.

Why not just synthesize each span separately and concatenate? Because that was tried, and the docstring records the scar tissue: XTTS degenerates on short text fragments — a lone word like "choice" comes back as babble or padded with seconds of silence — and per-span stitching produced choppy prosody and loudness jumps. Full-sentence renders keep the prosody natural; the trick is knowing where to cut them.

Step 3: forced alignment finds the cut points

Key concept — forced alignment

A speech recognizer answers "what was said?" A forced aligner answers an easier question: "given that this exact text was said, when was each word said?" The script uses torchaudio's MMS_FA aligner, which works on lowercase romanized words (a–z plus apostrophe) — which is exactly why the Japanese spans are romanized with fugashi + pykakasi first. English words and romanized Japanese words go through the same aligner uniformly.

Alignment yields a start/end sample for every word, and each word knows which span owns it. The boundary between span i and span i+1 is placed at the midpoint of the gap between span i's last word and span i+1's first word. Alignment gives a second gift: it reveals where real speech starts and ends, so XTTS's notorious end-of-clip hallucinated babble gets trimmed off every render. If alignment fails entirely, the script degrades gracefully to boundaries estimated from expected span durations (~13 chars/sec for English, ~7 for Japanese) and marks the sidecar alignment: "fallback" so you can filter on it later.

Step 4: emit the labels

After stitching, every output sample belongs to a known span, and every span has a language. Labels drop out by arithmetic: frame f covers samples [320f, 320f+320); its label is the language of the span containing its center sample. Here is the actual sidecar for our example, data/synthetic/cs-2/speaker_012_29b1e5a58d16/cs7395.json, abridged:

One optional refinement: --boundary-ambig-ms labels frames within a window of each switch point as 'a' (ambiguous), acknowledging that the precise switch instant inside a crossfade is guesswork. The training code treats only e/j as supervised.

Edge case — degenerate outputs

XTTS occasionally hallucinates: audio far longer than the text warrants, filled with babble. The script computes a duration budget from character counts and, if a render exceeds it, resynthesizes at progressively lower temperatures (0.7 → 0.5 → 0.35), keeping the shortest attempt if all three blow the budget. Japanese text also gets chunked below XTTS's ~70-character Japanese limit and concatenated. And speaker reference clips are loudness-normalized before conditioning, because several Common Voice references were so quiet they skewed the cloned voice.

One last detail matters enormously for the next-but-one section: output paths include the speaker, as in synthetic/cs-2/speaker_012_29b1e5a58d16/cs7395.flac, and update_pairs_csv_paths() rewrites the manifest's flat paths to match after generation. That directory name is what lets the training split guarantee that no speaker appears on both sides of the train/test line.

4Real Human Voices

Synthetic data has a lurking danger: a model trained only on XTTS output might learn to recognize XTTS rather than Japanese and English — the codec's texture, the crossfades, the cloned-voice artifacts. The antidote is real recordings from real people, and the repo contains two complete systems for collecting them: a one-command local recorder for Chris, and a full remote-contribution platform for everyone else.

The local recorder: just record

cmd/record/main.go opens the default microphone at 16 kHz mono, waits for you to speak, detects when you've finished, and writes data/manual/chris/sN.flac — numbering itself automatically. The interesting machinery is the voice-activity detector in internal/audio/vad.go: a small state machine fed 20 ms frames, using RMS energy against a threshold.

VAD states. Waiting→Speaking needs ~200 ms of loud frames; Trailing→Speaking on any loud frame; Trailing→Done after ~1.2 s of quiet.

The subtle touch is the pre-roll ring buffer. Speech onset detection needs ~200 ms of sustained energy before it triggers — by which time the first syllable has already happened. So while waiting, the VAD continuously records the last second into a ring buffer, and on trigger it flushes that buffer into the capture first. The attack of your first word survives. Symmetrically, at the end it keeps only 160 ms of the 1.2 s of trailing silence it needed to be sure you were done.

The remote system: signed links, a static site, and R2

Seventy-five clips of one person's voice risks a speaker-overfit model, so the project recruits friends. The design constraint is written into the planning doc: contributors are non-technical, and Chris refuses to do per-contributor cleanup. The solution spans four components and costs nothing to run:

Authentication is charmingly minimal. There are no accounts and no passwords — just a signed link. internal/token implements it in ~60 lines:

token = base64url({"name":"Laurie","exp":1730000000})
        + "." +
        base64url(HMAC-SHA256(secret, payload_b64))

The Go CLI signs tokens; the TypeScript Worker verifies them with the same shared secret (JANGLISH_HMAC_SECRET) and the same format — a deliberately boring two-implementation protocol. A token names one contributor and expires (default 7 days). If a link leaks, the blast radius is one person's upload prefix for a bounded time.

The browser side (web/app.js) has two touches worth noticing. First, audio capture doesn't trust the browser's sample rate: an AudioWorklet downsamples whatever the audio context provides to 16 kHz before WAV encoding, so uploads match the dataset format regardless of hardware. Second, sentences containing kanji are rendered with furigana — ruby annotations from a bundled reading table — because contributors like Laurie may need reading help with sentences such as:

Laurie|Let's meet at the 駅 at seven o'clock.
Laurie|新しいprojectを来週から始めます。

Progress lives in localStorage keyed by token, so closing the tab and reopening the link resumes exactly where the contributor left off. Meanwhile just list-progress shows Chris a one-line-per-contributor dashboard: assigned / staged in R2 / done locally.

Design principle — idempotence everywhere

Every command in this system can be re-run safely. contrib pull skips already-transcoded files and deduplicates CSV appends; rclone copy is a no-op on unchanged objects; deleting the WAV from R2 after transcoding means the staging area drains end-to-end and a re-pull can't double-process. The same philosophy shows up in the sentence generator (resumable buckets) and the audio factory (--skip-existing). Long-running data pipelines get interrupted; these are built to shrug it off.

One wrinkle: human recordings have sentences but no frame labels — nobody hand-labels 20 ms frames. Manual clips with code-switching therefore serve as evaluation material for the end-to-end pipeline (section 6), while a helper script generates LID sidecars for the single-language portions. With data flowing in from both factories, we can finally train the model.

5Training the Frame Classifier

With 31,634 labeled clips on disk, training ought to be the easy part: fine-tune a pretrained speech model, log some curves, save the best checkpoint. And structurally it is — cmd/train is a clean four-file affair (dataset, collator, model setup, loop). But each file contains one or two decisions that separate a model that seems to work from one that actually does. This section is about those decisions.

The model: stand on 436,000 hours of shoulders

The base model is facebook/wav2vec2-xls-r-300m — pretrained (self-supervised, no labels) on roughly 436k hours of speech across 128 languages. It already "knows" what Japanese and English sound like in its internal representations; fine-tuning just attaches a 2-class linear head (Wav2Vec2ForAudioFrameClassification) and teaches it which representation is which. The convolutional feature encoder — the part that turns raw waveform into frame vectors — is frozen: standard practice, a big speedup, and no observed quality loss.

↓frozen CNN encoder — 7 conv layers, total stride 320

Why 20 ms frames everywhere: the CNN stack's kernel/stride schedule (10,5)(3,2)(3,2)(3,2)(3,2)(2,2)(2,2) multiplies out to a stride of 320 samples. The dataset's 50 Hz labels were chosen to match this exactly.

The split: never test on a voice you trained on

Here is the most important honesty decision in the repo. Each synthetic speaker recorded many clips — and the same ~100 speakers appear across the en, jp, and cs-* subsets. If clips were split randomly, nearly every test clip would be spoken by a voice the model saw in training, and the model could lean on speaker-specific quirks. Test scores would be flattering and false.

So split_examples() splits by speaker group, using scikit-learn's GroupShuffleSplit twice: first carving held-out speakers from training speakers, then dividing the held-out set into validation and test. The group key is the speaker directory (speaker_012_29b1e5a58d16), which is exactly why the audio factory went to the trouble of putting every clip in a per-speaker folder. The code even refuses to run on flat paths: "run the speaker split migration before training."

Train ~70%
speakers 012, 047, 091, …
Validation ~15%
speakers 003, 058, …
Test ~15%
speakers 019, 072, …
Speaker-disjoint splits: every clip by a given voice lands entirely on one side of every line. The 97.7% test accuracy is measured on voices the model has never heard.

The collator: where the subtle bugs live

The collator's day job is boring — pad each batch's audio to a common length. But padding changes the frame count, and the sidecar's labels were written for the unpadded audio, so labels must be re-aligned to the model's output grid. _align_labels() does nearest-neighbor resampling: model frame t takes the label at source position (t + 0.5) × len(labels) / target_len. Padded frames beyond the real audio get an all-zero label vector — a deliberate "no supervision here" marker.

That marker meets its partner in the loss function:

mask = labels.sum(-1) > 0          # real frames have a one-hot label; padding is all zeros
targets = labels.argmax(-1)
loss = cross_entropy(logits[mask], targets[mask])

Only genuinely labeled frames contribute gradient. Padding is invisible to the optimizer.

War story — the 100 GB memory leak

The collator's length_bucket_samples = 8000 looks like a random knob. It is a tombstone. Padding each batch to its longest member yields a unique tensor shape almost every batch, and Apple's MPS backend caches a compiled graph per shape. Unbounded distinct shapes leaked ~100 GB of host memory over nine hours until macOS's jetsam killed the process. Rounding every batch up to a multiple of 0.5 s collapses thousands of shapes into a few dozen, and the graph cache stays bounded. The training loop carries matching scars: torch.mps.synchronize() before empty_cache() (an allocator race corrupted gradients into sudden permanent NaN), and a non-finite-gradient check that skips the optimizer step loudly rather than letting clip_grad_norm_ rescale every gradient to NaN and poison the weights.

The loop: small batches, honest checkpoints

The loop itself is hand-written PyTorch (no Trainer), tuned for a memory-constrained Mac: batch size 2 with 4-step gradient accumulation (effective batch 8), learning rate 1e-5 with linear warmup, three epochs, everything logged to Weights & Biases. Two evaluation cadences run in parallel: a quick eval on a fixed, seeded 200-example validation subset every 100 optimizer steps (comparable across steps because it's fixed), and a full validation pass at each epoch end, which is what actually selects the best model.

Checkpoint saving is atomic in the crash-safe sense: write to .tmp, rename the old checkpoint to .previous, rename .tmp into place, delete .previous. A crash at any instant leaves a loadable checkpoint on disk. Each checkpoint carries a training_checkpoint.json with its metrics and provenance — which is how we know the shipped model's exact report card:

{
  "checkpoint_kind": "final_full_validation_best",
  "epoch": 3,
  "metrics": {
    "accuracy": 0.9768,
    "f1_macro": 0.9760,
    "f1_per_class": [0.9804, 0.9716]   // [english, japanese]
  }
}

A frame classifier that's right 97.7% of the time on unseen voices, at 50 decisions per second. Time to see what it's for.

6The Payoff: LID-Guided Transcription

Everything so far built a referee. Now we put it on the field. Two scripts close the loop: cmd/train/predict.py turns raw frame decisions into usable segments, and cmd/eval/main.py uses those segments to make Whisper transcribe code-switched audio properly — and proves it with numbers.

From frames to segments

predict.py runs the model, softmaxes the logits, and takes the argmax per frame — 250 tiny decisions for a 5-second clip. Nobody downstream wants 250 decisions; they want spans. So consecutive same-label frames are grouped into segments, each with a start time, end time, and mean confidence:

$ just predict lid-wav2vec2-f1-98 data/synthetic/cs-2/speaker_012_29b1e5a58d16/cs7395.flac

000.82-002.18  e  confidence=0.97
002.18-003.49  j  confidence=0.99

004.06-004.94  j  confidence=0.99

When a sidecar exists, the script also scores itself against it, aligning label sequences of different lengths with the same nearest-neighbor trick the collator uses. But real model output is never this clean: a hard consonant or a breath can flip a frame or two, producing a 40 ms "English" blip inside a Japanese sentence. The eval pipeline's first move is therefore coalesce_segments(): repeatedly find the shortest segment, and if it's under 0.2 s, absorb it into its longer neighbor, re-merging until everything is plausible. Sub-second clips are exactly what makes Whisper hallucinate, so the blips must die first.

Three strategies, one winner

Given clean language segments, how should Whisper use them? The eval harness implements three strategies, and their ranking is a lesson in itself:

StrategyIdeaWhy it wins/loses
chopCut audio at LID boundaries; transcribe each piece in its languageLoses sentence context, clips phonemes at cut points, hallucinates on short clips. The naive baseline.
dualTranscribe the full audio twice (once en, once ja); keep each timestamped word only where the LID timeline says its language was spokenKeeps full context. But both passes run over everything, and word timestamps jitter.
spliceOne full pass in the dominant language; surgically splice in words from the other pass only where LID demands it — behind safety gatesThe default. Baseline behavior by construction, deviating only with evidence.

The splice strategy embodies the pipeline's core philosophy: never be worse than the baseline. First, sum up LID time per language. If the clip is English-dominant, run one English pass and stop — Whisper-en renders embedded Japanese as romaji ("Setsuyaku" for 節約), which is a faithful romanization, while a forced Japanese pass over mostly-English audio produces garbage. Asymmetry is the insight: the same trick doesn't work in reverse. Whisper-ja can only katakana-ize embedded English (「リップグロス」 for "lip gloss"), so Japanese-dominant audio gets a second, English pass, and the English LID spans get their words swapped in:

The four gates

A forced English pass over Japanese-dominant audio is a hallucination machine — it will cheerfully invent "I painted a nude color manicure" over a stretch of Japanese. So before an English span's words are spliced in, they must clear four gates, and failing any gate falls back to the ja-pass words for that span. Text is never dropped:

GateDefaultRejects
Span duration≥ 0.3 sTiny LID blips that survived coalescing — likely false positives
LID confidence≥ 0.85 meanSpans the referee itself isn't sure about
Word density≤ 3 words/secSix en-pass words crammed into 0.9 s — those words didn't really come from this span
Word probability≥ 0.5 meanWords Whisper's own decoder doubts
Key principle — fail toward the baseline

Every gate's failure mode is "keep what the single-language pass produced," never "output nothing." The pipeline can only ever replace baseline words with better ones; it cannot lose content. This is why the default strategy is safe to run over an entire dataset unsupervised.

One last subtlety in assembly: words are joined with spaces only between Latin words. Inserting spaces into Japanese text isn't cosmetic damage — it changes how fugashi tokenizes during scoring, which changes kanji readings ("新 しい" romanizes as shin shii instead of atarashii) and corrupts the metric itself.

Keeping score

How do you compare 「節約」 in the reference against "Setsuyaku" in a transcription without punishing a correct answer written in a different script? Normalize both sides to the same alphabet: anything containing Japanese is tokenized with fugashi and romanized with pykakasi, lowercased, and reduced to romaji tokens. Then jiwer computes word error rate and character error rate, and the harness prints a per-file and aggregate comparison — baseline Whisper versus the LID-guided pipeline, with improved/regressed/tied counts. The entire reason the LID model exists is to make that comparison come out favorably; every design choice in the previous five sections was in service of this one table.

The test cases are the documentation; several examples in this section came straight from them.

Where this leaves us

Step back and the shape of the project is pleasingly circular. An LLM writes sentences that a TTS model speaks, a forced aligner labels them, a speech model learns the labels, and the result teaches a transcription model to hear the way bilinguals actually talk. Four pretrained models, none of them retrained from scratch, arranged so that each covers another's blind spot. The craft is all in the joints: the loanword ban, the island counter, the dual-render stitch, the speaker-disjoint split, the splice gates. None of those decisions is glamorous. All of them are the difference between a demo and a system.
